# Dataset: stores and people flow

Reference for the project's data: the store dimension, the people-counter events, how they are assumed to be streamed into the pipeline, and the volume assumptions. All data is synthetic.

Pipeline steps and validation rules are in [`readme.md`](../readme.md) ("Data flow", "Validation rules"); this page doesn't repeat them.

## 1. Data model

| Object | Grain | Key | Defined in |
|---|---|---|---|
| `workspace.test02_streaming.dim_store` | One row per store | `store_id` (primary key) | `src/sql/01_create_dim_store.sql`, `02_populate_dim_store.sql` |
| `workspace.test02_streaming.simulated_event_source` | One row per message received | `source_topic` + `source_partition` + `source_offset` | `src/sql/04_create_simulated_event_source.sql`, `05_insert_simulated_events.sql` |

| `quarantine_people_counter_events` | One row per invalid event | none | Pipeline, `02_silver.py` |

| Column | Type | Rule |
|---|---|---|
| `store_id` | STRING, not null | `<country_code>-<city_code>-<nnn>`, e.g. `IT-MI-001`; `nnn` runs from `001` to the city's store count |
| `store_name` | STRING, not null | `Retail Store <city> <nnn>` |

### 2.4 Loading and changing it

All three scripts are in `src/sql/` and are safe to rerun.

1. `01_create_dim_store.sql` creates the schema and table if missing. On a table created before `macro_region` existed, it adds the column (checked in `information_schema`, because `ADD COLUMN IF NOT EXISTS` isn't supported).
2. `02_populate_dim_store.sql` merges the 200 stores: it inserts missing stores and fills or corrects `macro_region` on existing ones.
3. `03_validate_dim_store.sql` must return `PASS` on every row.

The pipeline reads `dim_store` as a static lookup, so updating it doesn't affect the stream.

## 3. People flow: how events reach the pipeline

### 3.1 Source

Each store has people-counter sensors at its entrances. A sensor emits one event each time it counts people going in (`ENTRY`) or out (`EXIT`).

In production the events are assumed to arrive through **Azure Event Hubs** (Kafka-compatible): one topic for the people counters, several partitions, one JSON message per event. Until that exists, `simulated_event_source` stands in for the topic: each row is one message, with the same envelope columns.

### 3.2 Message envelope

| Column | Meaning |
|---|---|
| `raw_event` | The JSON payload, unparsed |
| `source_topic` | Event Hubs topic; `people-counter-simulation` in the simulation |
| `source_partition` | Partition within the topic; `0` in the simulation |
| `source_offset` | Offset within the partition; unique per partition |
| `source_timestamp` | When the broker received the message (UTC) |

### 3.3 Payload

```json
{"event_id":"evt-000001","store_id":"IT-MI-001","sensor_id":"PC-MI-01",
 "event_timestamp":"2026-07-15T15:30:20.123","event_type":"ENTRY","people_count":1}
```

| Field | Meaning |
|---|---|
| `event_id` | Globally unique, immutable business id of the event |
| `store_id` | The store, as in `dim_store` |
| `sensor_id` | The counting sensor, `PC-<city_code>-<nn>` |
| `event_timestamp` | When the sensor counted, in the **store's local time**, without a time zone. Stored as `TIMESTAMP_NTZ`; convert with the store's `timezone_id` |
| `event_type` | `ENTRY` or `EXIT` |
| `people_count` | People counted in this event, at least 1 |

### 3.4 Delivery assumptions

- **At least once:** the broker or the sensor may resend a message. A resent message has the same topic, partition and offset, and is dropped at load (the `MERGE` in `05_…`).
- **Not in order:** events may arrive late or out of order across partitions; order by `event_timestamp` per store, not by arrival.
- **Append only:** the source is never updated or deleted, so bronze can read it as a stream.
- **Incremental:** each pipeline run reads only the messages that arrived since the last run.

## 4. Opening hours and time coverage

People are assumed to flow only while a store is open: **10:00 to 20:00 local time**, every day. Each store follows its own `timezone_id`, including daylight-saving time.

Because the stores span three macro regions, at least one region is open at every hour of the UTC day, so events arrive around the clock:

| Macro region | Open (UTC), winter | Open (UTC), summer |
|---|---|---|
| ASIA | 01:00 – 12:00 | 01:00 – 12:00 (no daylight saving) |
| EUROPE | 09:00 – 20:00 | 08:00 – 19:00 |
| AMERICAS | 15:00 – 04:00 (next day) | 14:00 – 03:00 (next day) |

The windows span the earliest opening and latest closing of the region's time zones (e.g. EUROPE winter: Central Europe opens 09:00 UTC, Lisbon closes 20:00 UTC). Two regions overlap from 01:00 to about 04:00 (ASIA, AMERICAS), 08:00/09:00 to 12:00 (ASIA, EUROPE), and 14:00/15:00 to 19:00/20:00 (EUROPE, AMERICAS).

## 5. Volume parameters

The number of visitors is a parameter per macro region:

| Parameter | Meaning | Default |
|---|---|---|
| `N_AVG_PEOPLE_EUROPE` | Average visitors per store per day, EUROPE stores | 3000 |
| `N_AVG_PEOPLE_AMERICA` | Average visitors per store per day, AMERICAS stores | 3000 |
| `N_AVG_PEOPLE_ASIA` | Average visitors per store per day, ASIA stores | 3000 |

A visitor is one person entering: the sum of `people_count` over a store's `ENTRY` events in a day. Each visitor is assumed to also leave the same day, so `EXIT` totals match `ENTRY` totals by closing time.

With the defaults:

| Scope | Visitors per day | Average per opening hour |
|---|---|---|
| One store | 3,000 | 300 |
| EUROPE (100 stores) | 300,000 | |
| AMERICAS (60 stores) | 180,000 | |
| ASIA (40 stores) | 120,000 | |
| **All stores** | **600,000** | |

Visitors are assumed to be spread evenly over the 10 opening hours unless a profile is defined later. The parameters aren't used by any code yet; they're the inputs for a future event generator.
