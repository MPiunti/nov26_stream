# Testing: what is checked before anything is deployed

Reference for the project's automated tests: the test strategy, what each test file checks, and how to run them. The rule that every change brings its test is in [`development.md`](development.md) §2.

## 1. Strategy: four layers

| Layer | What it proves | When it runs | Today |
|---|---|---|---|
| **1. Contract tests** | The parts agree with each other: bundles, pipeline code, SQL scripts, apps, the Genie definition and these documents. Standard library only: no Databricks connection, no table touched | On the PC before every hand-over, and in Databricks after every pull (`tests/run_tests`) | ✅ The `tests/` folder (§2) |
| **2. Logic tests on Spark** | The validation rules and transformations give the expected rows on test data | With every change, through Databricks Connect (already in `pyproject.toml`) | Planned |
| **3. Integration after deploy** | A deployed environment works end to end: the 8 test events of `05_…` give 5 silver rows and 3 quarantine rows; the metric views answer; the apps start | After every deploy to a test environment, before prod | By hand: the validation scripts in `src/sql/` and the checks of [`kpi_metrics.md`](kpi_metrics.md) §8 and [`kpi_genie.md`](kpi_genie.md) §5 |
| **4. Data quality in production** | Live data stays healthy | Continuously | Partly: every rejected row goes to quarantine with its reasons ([`pipeline.md`](pipeline.md) §2); alerts on quarantine volume and freshness planned |

**The gate for production:** layers 1 and 2 on every change, layer 3 after the deploy to a test environment, and prod only when all three pass. Running them in a CI workflow is part of the move to one bundle ([`decisions.md`](decisions.md) D12).

## 3. Running them

- **On a PC:** from the repo root, run `python -m unittest discover -s tests`. It takes about two minutes, most of it the time-zone tests.
- **In Databricks:** open `tests/run_tests` in the Git folder, attach serverless compute and click **Run all**. It fails if any test fails.

**What the tests don't cover yet:** Spark itself, the parsing results on real data, and the deployed pipeline (layers 2 and 3 of §1). Those are checked today by running the pipeline and the validation scripts in `src/sql/`.
